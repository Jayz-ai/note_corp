# 500円ライン（リサーチ型の量産ライン）

読者が実際に書いている悩みをリサーチし、「4,000字で答えが出る500円記事」を複数本まとめて作るライン。
通常の企画（企画書 → CEO採用 → 制作）とは別の流れで、`/run-500yen-line` で回す。

> 出どころ: 別スレッド「AI社員4人で500円note量産」のワークフローを精査して取り込んだもの。
> 4人の担当（ネタ拾い・タイトル・執筆・検品）は、既存の4部署に割り当てた。
> X の巡回は、CEO の PC 上の朝8時のルーティンが担当する（`ops/routines/x-scan-daily.md`）。

## 担当と成果物

| 工程 | 担当部署 | 成果物 |
|---|---|---|
| ① リサーチ・テーマ選定 | 企画部 `planner` | `content/runs/<run>/01_themes.md` |
| ② タイトル | マーケティング部 `marketer` | `content/runs/<run>/02_titles.md` |
| ③ 執筆 | 制作部 `writer` | `content/drafts/<日付>-<slug>/article.md` |
| ④ 検品・審査 | 編集・品質部 `editor` | 同じフォルダの `review.md` |
| まとめ | COO | `content/runs/<run>/report.md` |

`<run>` は実行日（`YYYY-MM-DD`）。同じ日に2回目を回すときは `YYYY-MM-DD-2` にする。

## 決裁の位置
- このラインで作る記事は、記事ごとの企画書を CEO が採用する工程を省く（CEO の決定: `org/decision-log.md`）
- CEO が判断するのは公開の時点だけ。`ready` になった記事から、出すものを CEO が選ぶ
- 本数は1回あたり既定3本、最大10本。それ以上は CEO の決裁が必要

## ① リサーチ・テーマ選定（企画部）

### リサーチの方法
1. `content/runs/inbox/x-scan-*.md` があれば最初に読む。朝8時の X 巡回ルーティン（`ops/routines/x-scan-daily.md`）が選んだテーマなので、そこから採用基準を満たすものを選ぶ。件数・取得手段はそのファイルの記載を引き継ぎ、自分で読んだ件数と分けて書く
2. CEO が `content/runs/inbox/` に置いたそのほかの素材（X やコミュニティで見た悩みのメモなど）を読む
3. テーマが本数に足りないときだけ、WebSearch で、悩みが本人の言葉で書かれている場所（Q&A サイト、掲示板、ブログのコメント、SNS の公開投稿）を探す
   - 検索語の例: 「〇〇 どうすればいい」「〇〇 続かない」「〇〇 向いてない」「〇〇 やめたい」「〇〇 しんどい」
4. 悩みとして読めたものだけを数える。宣伝・ネタ投稿・野次は数えない。目標は30件以上。届かなければ実数を書く
5. 似た悩みでまとめ、下の基準でテーマを絞る

### 採用基準（すべて満たすこと）
- **4,000字で答え切れる**: 原因が1〜2個に絞れ、解決策が3つ以内の手順にできる。広すぎる悩みは狭く切り分ける
- **今日やれる行動で終われる**: 読み終えてから30分以内に始められる一歩がある
- **1年後も同じ悩みがある**: ニュース・制度改正・ツールのバージョン・流行に依存しない
- **500円払ってでも今すぐ答えが欲しい**: 複数の場所で同じ悩みが繰り返し出ている

### 採用しないテーマ
- 医療・メンタル疾患の診断や治療、法律トラブル、個別の投資判断（専門家の領域）
- 特定の個人・企業への攻撃が前提のもの
- 答えが「人による」で終わるもの
- 直近30日の run と `content/published/` に同じテーマがあるもの

### 禁止
- 読んでいない投稿を件数に入れない
- 投稿本文の転載や、アカウント名など個人が特定できる情報を書かない。悩みは自分の言葉で要約する

### 出力形式（`01_themes.md`）
冒頭に「読んだ件数 / 使った検索語 / 参照した URL の一覧（個人の投稿の URL は除き、サイト名とページの種類まで）」を書き、続けて:

```
## テーマ01: （「〜な人が〜できない」の形で一文）
- slug: （半角英小文字・数字・ハイフン）
- 読者像: 誰が、どんな場面で困っているか
- 悩みの核心: 本人が気づいていない本当の詰まりどころ
- 答えの骨子: 原因1行 → 解決策3つ以内 → 今日やること1つ
- 根拠: 同じ悩みが何件あったか、どこで見たか（要約のみ）
- 鮮度リスク: 1年後に古びる要素（なければ「なし」）
```

## ② タイトル（マーケティング部）

テーマごとに **「1分で読めそう」と思わせるタイトル** を5案出し、**衝動買いされやすい順** に並べる。

### 作り方
- 28字以内が目安（スマホで2行に収まる長さ）
- 答えの数を小さく見せる（「1つだけ」「3つ」）。数は ① の骨子と一致させる
- 読者が普段使う言葉で書く。専門用語・カタカナの造語・抽象語（「本質」「マインド」）は避ける
- 悩みの場面が一瞬で浮かぶ具体的な言葉を入れる（「日曜の夜」「上司への返信」）

### 採点（各5点、合計25点で並べる）
1. **自分ごと**: 読者が1秒で「これは自分だ」と思うか
2. **答えの気配**: 中に具体的な答えがあると伝わるか
3. **軽さ**: すぐ読み終わりそうか
4. **500円の納得感**: ランチ1回分より得だと感じるか
5. **意外性**: 「頑張れ」のような予想どおりの答えではなさそうか

### 禁止
- 保証する表現・時期に依存する表現（④ の禁止語と同じ）
- 本文で回収できない約束。数字と約束は ① の骨子で回収できる範囲に限る
- 不安を煽るだけの言い回し

### 出力形式（`02_titles.md`）
```
## テーマ01: （テーマ文）
| 順位 | タイトル | 自分ごと | 答え | 軽さ | 納得 | 意外 | 計 |
|---|---|---|---|---|---|---|---|
（5案）
- 採用: 1位のタイトル
- 1位の理由: 一文
```

## ③ 執筆（制作部）

`scripts/new-article.sh <slug> 500 "<採用タイトル>"` で記事フォルダを作り、4段構成で書く。

| 段 | 字数の目安 | 公開範囲 | 中身 |
|---|---|---|---|
| ① 共感 | 約800字 | **無料** | 読者の場面を具体的に描き、「あなたのせいではない」まで言う。答えはまだ出さない |
| ② 原因 | 約1,000字 | 有料 | なぜそうなるのか。原因は1〜2個に絞り、仕組みで説明する |
| ③ 解決策 | 約1,600字 | 有料 | 3つ以内。それぞれ「何を・どうやって・つまずいたら」まで書く |
| ④ 今日やること | 約600字 | 有料 | 30分以内にできる一歩を1つ。所要時間と最初の動作まで指定する |

合計は3,800〜4,200字。

### 有料ラインの切り方
- 無料部分は ① 共感まで。**答えの直前で切る**
- ① の最後の2〜3文では、答えがあることと、その形（原因がいくつ・解決策がいくつ・今日やること）だけを見せる
- 無料部分に原因や解決策の中身を出さない。それでも、無料部分だけで「わかってもらえた」と感じられる読み物にする

### 文体
- です・ます調。一文は60字以内が目安。スマホで読みやすいよう、2〜3文で改行する
- タイトルで約束した数字と内容は本文で必ず回収する

### 禁止
- 架空の体験談、実在しない統計、出典のない数値、存在しない研究の引用。例を出すときは「たとえば」と仮の場面であることを示す
- 投稿の転載や、元の投稿者が特定できる書き方
- 医療・法律・投資の個別判断。必要なら「専門家に相談を」の一文に留める

## ④ 検品・審査（編集・品質部）

1. `scripts/check-article.py <article.md>` を実行し、出力を `review.md` に貼る
   - 禁止語（保証表現・時期依存の表現）を全件検出する
   - 字数（無料部分・全体）と有料ラインの有無を確認する
2. 禁止語は editor が直接言い換えてよい（このラインでの例外）。修正前→修正後を `review.md` に全件書く
   - 断定 → 条件つきの言い方にする（「絶対うまくいく」→「うまくいきやすくなる」）。削っても意味が通るなら削る
   - 時期依存 → 時期に依らない言い方にする（「2026年最新の方法」→「この方法」）。「いまの方法」のような言い換えも時期依存なので不可
   - 言い換えで主張が弱くなり、解決策がぼやけたら、具体的な手順を足すよう制作部に差し戻す
3. もう一度 `check-article.py` を実行し、**エラー0件** を確認する。0件でなければ合格にしない
4. `templates/review.md` で採点する。合格なら `ready`、構成から崩れていれば `draft` に戻して差し戻す
